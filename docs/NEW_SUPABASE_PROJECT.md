# Moving to a fresh Supabase project

Written 2026-09-05, the day the free plan's 5 GB egress allowance ran out in four days
(7.67 GB) with one active user and a 36 MB database. The org was restricted, which takes the
whole app down, and the allowance only resets on the billing cycle date (01 Oct).

The cause was ours and is fixed in commit `377d9d5` — pg-boss polled 13 queues every 2s
forever, and the dashboard's live panels kept polling in background tabs. **Deploy that before
or right after this move**, otherwise the new project's allowance goes the same way.

---

## 0. Create the project in a NEW organization

The quota is **per organization**, not per project. A new project inside
`Samiullislam09's Org` shares the exhausted allowance and will be restricted too.

- Supabase → organization switcher → **New organization** (Free plan)
- Inside it → **New project**
- Region: **ap-southeast-1 (Singapore)** — same as before, closest to us
- Save the database password it shows you. It is shown once and you need it in step 3.

While you are there: in the old org, **pause** `Samiullislam09's Project`. A free org allows
two active projects, and a paused project uses no egress.

---

## 1. Run the schema

23 migrations, in numeric order, from `supabase/migrations/`. They are not optional and the
order matters (002 sets embeddings to 1024 dimensions, 022 moves them to 2048).

Easiest: SQL Editor → paste the combined file (`ALL_MIGRATIONS.sql`, generated by
concatenating the folder in order) → Run. If it stops on an error, run the files one at a time
from 001 and stop at whichever fails — that error is the real message.

`001_init.sql` creates the `vector` and `pgcrypto` extensions itself, so there is nothing to
enable by hand first.

Check afterwards, in the SQL editor:

```sql
select count(*) from information_schema.tables where table_schema = 'public';
-- expect ~20 tables: tenants, memberships, site_pages, content_items, jobs_log,
-- schedules, site_profiles, site_audits, brain_tasks, media, ...
```

## 2. Storage

Nothing to do. `agent-server/src/lib/media/store.ts` creates the public `media` bucket on
first use (5 MB limit, webp/jpeg/png) because a migration cannot create buckets.

## 3. Collect the four values

From the new project:

| Value | Where in the dashboard |
|---|---|
| Project URL | Settings → API → Project URL |
| `anon` public key | Settings → API → Project API keys |
| `service_role` secret key | Settings → API → Project API keys (never goes in the browser) |
| Connection string | Settings → Database → Connection string → **Session pooler** |

The connection string is the one with your password in it. Use the **session** pooler, not
the transaction one: pg-boss's NOTIFY listener (`useListenNotify`, `agent-server/src/db.ts`)
needs a session-pinned connection, and transaction pooling silently disables it — the queue
still works, it just falls back to polling.

## 4. Put them in the three places

**Local web** — `.env.local`:
```
NEXT_PUBLIC_SUPABASE_URL=https://<new-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
SUPABASE_SERVICE_ROLE_KEY=<service_role key>
```

**Local agent-server** — `agent-server/.env`:
```
DATABASE_URL=<session pooler connection string>
SUPABASE_URL=https://<new-ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service_role key>
```

**Railway** → the `ai-Automation-sass-` service → Variables: the same three as agent-server.
Everything else there (NVIDIA, Cloudflare, DataForSEO, AGENT_SERVER_TOKEN, WEB_APP_URL,
CORS_ORIGIN) is unrelated to Supabase and stays as it is.

Leave `CREDENTIALS_ENCRYPTION_KEY` alone. Change it and every stored Google refresh token
becomes unreadable.

## 5. Auth

Authentication → URL Configuration:
- **Site URL**: your deployed web app URL (or `http://localhost:3000` while developing)
- **Redirect URLs**: add `http://localhost:3000/auth/callback` and the deployed
  `<app>/auth/callback` — `components/AuthCard.tsx` sends both the Google button and the
  signup confirmation mail there.

Google sign-in (Authentication → Providers → Google) is a separate switch from the Search
Console integration; turn it on only if you want the "Continue with Google" button to work.
The Search Console side uses `GOOGLE_CLIENT_ID/SECRET/REDIRECT_URI` in the web app's env and
does not touch Supabase Auth.

## 6. Do you need the old data?

Probably not. The database was 36 MB with one user: the expensive things in it — crawled
pages, the Site Brain, audits — are all rebuilt by running the crawler once, for free. The
simple path is: sign up again, connect the website, press **Fill it in for me** on Site Brain.

If you want the written articles and the brain history instead, do this BEFORE the old project
is deleted (a restricted project can still be dumped):

```bash
pg_dump "<old session pooler URL>" --data-only --schema=public \
  --exclude-table=jobs_log --exclude-table='pgboss.*' > old-data.sql
psql "<new session pooler URL>" -f old-data.sql
```

Data only, into a schema the migrations already built. Users are a separate story: they live in
`auth.users`, which a `--schema=public` dump does not carry, so signing up again is simpler
than moving one account.

## 7. Check it end to end

```bash
npm run dev                       # web
cd agent-server && npm run dev    # queue + agents
```

- Sign up → you should land on onboarding, not an error
- Connect a website → Site Brain → **Fill it in for me**
- The progress bar should move through "Finding your pages → Reading them → …"; if it sits on
  "Queued" for more than 30 seconds, the agent server is not connected to the same database
- In the agent-server log, `[db] connecting to …` must show the NEW project ref

## 8. Keep the new allowance

5 GB a month is plenty for real use — it was idling that ate it, not people.

- Deploy commit `377d9d5` to Railway (NOTIFY + 30s polling instead of 2s)
- Do not leave `npm run dev` running overnight; local dev hits the same production project
- Watch Org → Usage → Egress in the first week. Flat while nobody is using the app is what
  correct looks like now.
