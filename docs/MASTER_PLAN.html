3 · Paanch usool jo kabhi nahi tootenge

Ye product ke usool hain, code ke nahi. Har feature, har agent, har reply in paanch se guzarega. Top-20 company ka matlab feature zyada nahi hota — matlab hota hai ki user ko kabhi “ye kya hua?” na sochna pade.

1

Samjho, phir karo. Shak ho to poochho — par sirf ek baar, sirf ek sawaal.

Har order ko structured intent me badla jayega, jisme confidence aur missing fields hain. Confidence kam ya koi zaroori cheez missing → ek chhota sa sawaal (“Kis topic pe?” / “Publish bhi karun ya Approvals me rakhun?”). Kabhi teen sawaal nahi. Kabhi “kya aap sure hain?” nahi — wo irritate karta hai.

2

Jo irreversible hai, wo pehle wapas bolo.

Publish live site pe, sab cancel, 10 article ek saath — inse pehle system ek line me dohrata hai jo samjha (“3 article, roz subah 9 baje, seedha site pe — theek?”). User “haan” bole to hi. Draft likhna, keyword research — ye reversible hain, seedha karo.

3

“Ho gaya” sirf database bol sakta hai, model nahi.

Reply ke jo hisse kaam ke baare me hain (“queued”, “published”, “scheduled for 9:40”), wo code task row padh ke banata hai. Model sirf baatcheet karta hai, aur uske paas confirm karne ke lafz nahi hain — structurally: model ka output aur system ka status do alag channel hain jo UI me alag dikhte hain.

4

Har kaam ka ek ID, ek timeline, ek undo.

Har order ek task hai jiska status user chat me, office me, aur Schedule page pe ek jaisa dikhta hai — teen jagah, ek row. Har task “kyun ruka / kya hua / kitna time” batata hai. Aur jo cancel ho sakta hai, wo ek click me cancel hota hai.

5

Fail ho to zor se, chupke se kabhi nahi.

Aaj migration 016 ke bina orders silently kabhi nahi fire hote — ye class of bug ban hai. Har agent ka har run agent_runs me likha jaata hai, aur har failure user ko ek line me plain language me dikhti hai (“Site ne crawl block kar diya — 20 min me dobara try karunga, ya aap robots.txt check karo”).

5 · Mr Lxwa — ek dimaag

Ye wo service hai jo sab kuch samajhti hai. Chaar hisse, ek process.

5.1 Intent Engine — “user ne kya kaha”

Aaj ka regex + chhota classifier rahega (fast path — 0ms, ₹0), par uske upar ek structured extractor jo manifests ki list dekh kar kaam karta hai. Output hamesha ye shape:

{
  "action":     "write_article",         // manifest me registered koi bhi action
  "agent":      "writer",                // registry se
  "params":     { "topic": "solar panels for homes", "count": 1 },
  "when":       { "at": "2026-08-27T16:40:00Z", "kind": "relative", "matched": "40 min baad" },
  "delivery":   "approvals" | "publish", // kahan jaayega
  "confidence": 0.92,
  "missing":    [],                      // e.g. ["topic"] → ek sawaal
  "irreversible": false,                 // true → pehle confirm
  "echo":       "1 article on solar panels for homes, 40 min baad, Approvals me"
}
  • when aaj ke lib/when.ts se aata hai — code, model nahi. Waqt guess nahi hota. (26 tests already green.)
  • action sirf registry me registered actions me se ho sakta hai — model kuch aur likhe to none.
  • confidence < 0.75 ya missing non-empty → ek sawaal. Kabhi guess karke paisa nahi jalega.
  • irreversible manifest se aata hai (publish = true, draft = false).
  • echo wo line hai jo confirm karte waqt dikhegi — user ki bhasha me.

Model (tay, measured — §18.4b)

Intent Engine aur Conversation dono openai/gpt-oss-120b pe (NIM free, reasoning_effort:"low"), fallback Nemotron. Config ek jagah: lib/chat-model.ts — brain me ye file jaisi-ki-taisi jaati hai. Writer/judge ka model alag hai aur Phase 2 test se tay hoga.

5.2 Conversation — Q&A ka jawab kaun deta hai

Aapka sawaal tha: “maine koi bhi Q&A diya to kaun answer dega?” Jawab: Mr Lxwa ka conversation model — par ab wo andha nahi hoga. Usko har turn pe ye milega:

  • Registry: kaun se agents hain, kya kar sakte hain (to “kya tum leads dhund sakte ho?” ka sahi jawab de)
  • Live task list: kya chal raha hai, kya booked hai, kya fail hua (to “kya update hai?” sach ho)
  • Business context: onboarding + crawled site (aaj ki tarah)

Aur usse teen cheezein chheen li jaayengi: confirm karne ke lafz, ✓/✕ symbols, aur kaam shuru karne ka koi raasta. Wo sirf bolta hai. Ye aaj partially hai (regex filter), naye me structural hoga — model ka text aur system ka status UI me do alag blocks hain.

5.3 Planner — ek order, kai steps

“3 article likh ke publish kar do” = 1 task, N steps. Planner intent ko steps me todta hai manifests dekh kar (kaunsa agent kis input se kaunsa output banata hai). Ye deterministic code hai, LLM nahi — chain fix hai, sirf params badalte hain.

5.4 Orchestrator — chalata hai, yaad rakhta hai, wapas uthata hai

  • Har step ek pg-boss job; step ka result task_steps.output me, agla step usi se input leta hai
  • Crash ke baad restart → jo step done nahi wahi se resume (idempotency key = task_id:step_no)
  • Retry: 3 baar, 1s/4s/16s backoff, phir task needs_attention + user ko ek line
  • Per-tenant daily caps (aaj ke config/caps.ts ki tarah) — cap lage to user ko wajah dikhe, chupke se drop nahi
  • Scheduled orders: aaj ka tickOrders() yahi rahega, bas scheduled_orders ki jagah tasks.run_at

5.5 Kaun pehle, kaun baad — kaun tay karta hai v5

Seedha jawab: Planner tay karta hai, aur Planner LLM nahi hai — code hai. LLM sirf ye batata hai ki user ne kya maanga (tool call). Uske baad kaun-kis-order-me ka jawab har agent ke manifest me likhe needs se nikalta hai. Wahi order har baar, kyunki usme sampling nahi hai.

6 · Agent contract — har agent ka ek hi shape

Ye wo cheez hai jo “har agent alag repo me” ko mumkin banati hai bina brain ko har baar badle. Har agent — chahe Python ho ya TS, chahe andar gpt-researcher ho ya Playwright — bahar se bilkul ek jaisa dikhta hai.

6.1 Teen endpoints, bas

GET  /health     → { ok: true, version, uptime }
GET  /manifest   → (neeche)
POST /run        → body: { run_id, tenant_id, action, input, context, callback_url }
                   reply: 202 Accepted turant; result callback_url pe POST hota hai

/run turant 202 deta hai kyunki gpt-researcher ek article me 3-8 minute leta hai — HTTP timeout ka sawaal hi khatam. Agent kaam khatam kar ke brain ke callback_url pe result POST karta hai. Brain 30 min me callback na aaye to run ko failed maanta hai (heartbeat optional).

10 · Chat UX rules — top-20 company grade

Ye rules code me enforce honge (tests ke saath), prompt me nahi. “User confuse ya irritate na ho” ka matlab ye 9 cheezein hain.

1. Do channel, ek bubble nahi

Model ki baat aur system ka status UI me alag dikhte hain: status ek card hai (icon, state, countdown, Cancel), model ka text uske neeche. User ko kabhi sochna nahi padta “ye sach hai ya AI bol raha hai”.

2. Echo before irreversible

Publish / sab cancel / 5+ articles → ek line echo + “Haan” button. Chat me “haan/ok/kar do” bhi chalega. 2 min me jawab nahi → order expire, kuch nahi hota.

3. Ek sawaal, kabhi do nahi

missing me ek se zyada ho to sabse zaroori ek poochho, baaki default. “Kis topic pe?” — bas. Options ho to chips dikhao, type na karwao.

4. Waqt hamesha do tarah

“9:40 PM pe (38 min baad)”. User ke timezone me. Countdown live. “Scheduled” akela kabhi nahi.

5. Har order ki receipt

Order accept hote hi: kya, kab, kahan land hoga, kitna time, Cancel. Ye tasks.echo + state se banta hai — model se nahi.

6. Failure = wajah + agla kadam

“Ruk gaya” kabhi akela nahi. “Site ne crawl block kiya — Retry, ya robots.txt me hamara UA allow karo.” Dev-level error message_dev me, user ko nahi.

7. Sawaal ka jawab sawaal ka

“mera schedule kya hai” → schedule. Kuch badalta nahi. Aaj ke 30 control tests isko already guard karte hain; ye suite naye system me bhi chalegi.

8. Bhasha user ki

Hinglish me poochha → Hinglish me jawab. Status cards bhi (“Booked”, nahi “Enqueued”). Kabhi system ke lafz nahi: queue, job, enqueue, worker, pg-boss.

9. Undo dikhaya jaaye

Jo cancel/unpublish ho sakta hai, uska button status card pe hi hai. User ko poochhna na pade “ab wapas kaise lun?”
