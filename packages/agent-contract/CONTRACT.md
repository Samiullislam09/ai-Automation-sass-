# The MrLxwa Agent Wire Contract — v1

This is the normative document. `@mrlxwa/agent-contract` is one implementation of it (TypeScript);
a Python, Go or Rust agent that follows this file is a first-class agent and needs nothing from the
npm package. Every per-agent repo is built against this document.

Every JSON block below was **captured from a real run** of `examples/echo-agent` (`npm run example:echo`,
`AGENT_TOKEN=echo-dev-token`, `PORT=7801`) on 2026-08-27, not written by hand.

- Version: **1** (this document). Breaking changes bump it; additive fields do not.
- Transport: HTTP/1.1, JSON only, UTF-8. `content-type: application/json` on every request with a body.
- The brain is the **client** for `/health`, `/manifest`, `/run`; the agent is the **client** for callbacks.
  Both directions authenticate with the same shared secret.

---

## 1. Vocabulary

| Term | Meaning |
|------|---------|
| **brain** | The orchestrator. Owns the DB, the user, the plan, the retries. Never runs agent logic. |
| **agent** | One process serving one manifest. Stateless between runs, owns no DB, writes no user-facing copy. |
| **action** | One capability of an agent, e.g. `write_article`. The unit the planner schedules. |
| **run** | One execution of one action, identified by a `run_id` the brain generates. |
| **event** | An in-flight observation of a run (step, progress, data item, log). |
| **result** | The single terminal message of a run: success + output, or failure + retryability. |

Hard rules an agent must obey:

1. **The agent never writes user-facing copy.** It emits `log` lines for developers and structured
   `data` payloads for the UI; the brain renders user text from `manifest.actions[].user_messages`.
2. **The agent never touches the brain's database** and never calls back on any URL except the
   `callback_url` it was given for that run.
3. **`/run` never blocks.** It validates, accepts, and returns `202` — the work happens after the response.
4. **A run produces exactly one result message.** Zero results is a bug; two is a bug.
5. **Events are user-meaningful, not token-by-token.** One `data` event per keyword / section / image /
   lead. A 2 000-word article is a handful of events, not two thousand.

## 2. Endpoints

```
GET  /health    → 200
GET  /manifest  → 200
POST /run       → 202 | 400 | 401 | 409
*               → 404
```

Path matching ignores the query string and a trailing slash. Anything else is `404` with the route list.

### 2.1 `GET /health`

No authentication (the platform's own health checker must be able to call it).

```http
GET /health HTTP/1.1
```
```http
HTTP/1.1 200 OK
content-type: application/json
content-length: 40

{"ok":true,"version":"1.0.0","uptime":2}
```

| Field | Type | Meaning |
|-------|------|---------|
| `ok` | `boolean` | `false` (or a non-200) means: do not schedule work here. |
| `version` | `string` | Must equal `manifest.version`. |
| `uptime` | `number` | Whole seconds since the process started. |

The brain treats `ok !== true` as unhealthy even on a 200.

### 2.2 `GET /manifest`

No authentication. Returns the manifest verbatim (§4). The brain **must** validate it and refuse to
register an agent whose manifest fails; a bad manifest is a deploy-time failure, never a runtime surprise.

```http
GET /manifest HTTP/1.1
```
```http
HTTP/1.1 200 OK
content-type: application/json
content-length: 625

{"id":"echo","name":"Mr. Echo","version":"1.0.0","description":"Says your text back to you, one word at a time. The reference agent for the contract.","actions":[{"id":"echo","phrases":["echo karo","repeat after me","say this back","yeh dobara bolo"],"input":{"text":"string","delay_seconds":"number?"},"output":{"text":"string","steps":"number"},"irreversible":false,"estimated_seconds":5,"cost_units":0,"needs":[],"provides":"echo","user_messages":{"started":"Echoing {text}","progress":"{count} words echoed","done":"Echoed {text}","failed":"Could not echo that"}}],"office":{"room":"echo","ico":"🪞","color":"#4cc9f0"}}
```

Note `"provides":"echo"` in the response even though the source manifest omits it: `provides` defaults
to the action `id` and the agent serves the **normalised** manifest, so the brain never has to guess.

### 2.3 `POST /run`

Authenticated. Starts a run and returns immediately.

**Request**

```http
POST /run HTTP/1.1
content-type: application/json
x-agent-token: echo-dev-token

{
  "run_id": "run_2026_08_27_a1b2c3",
  "tenant_id": "tenant_demo",
  "action": "echo",
  "input": { "text": "hello from the brain", "delay_seconds": 1.2 },
  "context": { "locale": "en", "site_profile": { "domain": "example.com" } },
  "callback_url": "http://127.0.0.1:9911/agents/echo/callback"
}
```

| Field | Type | Required | Rule |
|-------|------|----------|------|
| `run_id` | `string` | yes | Non-empty. Generated by the brain. The idempotency key (§2.4). |
| `tenant_id` | `string` | yes | Non-empty. Echoed on every event; the agent must not use it to reach a DB. |
| `action` | `string` | yes | Must be an `id` in the manifest. |
| `input` | `object` | yes | Validated against `actions[].input` **after** the 202 (§3.1). |
| `context` | `object` | no | Free-form brain-supplied context: site profile, ICP, tenant style, per-run credentials. Defaults to `{}`. Never validated. |
| `callback_url` | `string` | yes | Absolute `http://` or `https://` URL. Every message for this run goes here and nowhere else. |

**Response — 202, in 38 ms for a run that took 1 259 ms**

```http
HTTP/1.1 202 Accepted
content-type: application/json

{"accepted":true,"run_id":"run_2026_08_27_a1b2c3"}
```

The brain asserts `accepted === true` and `run_id` equal to what it sent; anything else is a protocol error.

**Error responses** (all real, from the echo agent):

| Status | When | Body |
|--------|------|------|
| `401` | Missing or wrong `x-agent-token` | `{"error":"unauthorized"}` |
| `400` | Malformed body | `{"error":"invalid run request","details":["callback_url must be an http(s) URL","input must be an object"]}` |
| `400` | Unknown action | `{"error":"unknown action \"shout\"","actions":["echo"]}` |
| `400` | Unparseable JSON | `{"error":"body must be valid JSON"}` |
| `409` | `run_id` already seen by this process | `{"error":"duplicate run_id","run_id":"run_2026_08_27_a1b2c3"}` |
| `413` | Body over the host's limit (2 MB in the example) | `{"error":"body too large"}` |
| `404` | Any other route | `{"error":"not found","routes":["GET /health","GET /manifest","POST /run"]}` |

A `4xx` from `/run` means **no callback will ever arrive**. The brain must fail the task on the spot
rather than waiting for the watchdog. (The e2e test asserts exactly this for the 401 case.)

### 2.4 Idempotency

`run_id` is the idempotency key. An agent that has already accepted a `run_id` answers `409` and starts
nothing. The in-process implementation remembers the last 10 000 ids; a multi-replica deployment should
back this with a shared store, or accept that dedupe is per-replica and let the brain's own
`run_id`-unique constraint be the real guard. `409` is **not** an error for the brain: it means "already
running, wait for the callback you are already going to get".

## 3. Authentication and signatures

### 3.1 Inbound (`/run`)

Header `x-agent-token` must equal the agent's shared secret, compared in **constant time**
(`timingSafeEqual` on equal-length buffers; unequal lengths are an immediate reject). `/health` and
`/manifest` are unauthenticated on purpose: they leak only what the agent can do, never tenant data.

### 3.2 Outbound (callbacks)

Every callback POST carries:

| Header | Value |
|--------|-------|
| `content-type` | `application/json` |
| `x-agent-token` | The same shared secret — proves the POST came from the agent. |
| `x-agent-id` | `manifest.id`, e.g. `echo`. Lets the brain route without parsing the body. |
| `x-run-signature` | `HMAC-SHA256(secret, run_id + "." + status)`, lowercase hex, 64 chars. |

`status` is exactly one of:

- `"event"` — for `{"kind":"event"}` messages
- `"ok"` — for a `{"kind":"result"}` whose `result.ok` is `true`
- `"error"` — for a `{"kind":"result"}` whose `result.ok` is `false`

The signing secret defaults to the agent token and may be configured separately (`callbackToken`) when
the brain wants inbound and outbound secrets rotated independently.

**Worked example** — secret `echo-dev-token`, run `run_2026_08_27_a1b2c3`:

```
HMAC-SHA256("echo-dev-token", "run_2026_08_27_a1b2c3.event")
  = 3afa56703615e23f05aa9294764eecd8ae42aad0aa79fe6b70206fca31d9e10c
HMAC-SHA256("echo-dev-token", "run_2026_08_27_a1b2c3.ok")
  = 55802208f7209b1021abadf253f9052faabbfe5e51e52882bdb22205c74660db
```

Both hex strings appear verbatim in the captured callbacks in §5.

Verification on the brain side, in order:

1. Reject if the signature is not 64 hex characters.
2. Derive `status` **from the body you received** (`kind`, and `result.ok`), never from a header.
3. Compare `HMAC-SHA256(secret, run_id + "." + status)` to the header in constant time.
4. Reject if `run_id` in the body does not match the run the URL/route is for.

Because the signature binds `run_id` **and** `status`, an attacker who replays a real `…ok` callback
cannot re-label it as an `error` (or vice-versa) — the e2e test asserts a valid `ok` signature fails
verification against `"error"`, against a different `run_id`, and against a different secret.

The signature does **not** cover the body. It is an authenticity and status-binding token, not a payload
MAC; TLS is what protects the payload in transit. Implementations that need payload integrity should add
a body HMAC in a new header rather than redefine this one.

## 4. The manifest

### 4.1 Shape (prose schema)

Top level — all required:

| Field | Type | Rule |
|-------|------|------|
| `id` | string | Matches `^[a-z][a-z0-9_]*$`. Globally unique across agents. This is the routing key. |
| `name` | string | Non-empty. Human display name, e.g. `Mr. Writer`. |
| `version` | string | Semver `MAJOR.MINOR.PATCH` with optional `-prerelease` / `+build`. Must equal `/health`'s `version`. |
| `description` | string | Non-empty. One sentence; the router shows it to the planner. |
| `actions` | array | At least one `ActionSpec` (below). Action `id`s must be unique within the manifest. |
| `office` | object | `{ room: string, ico: string, color: string }`. `color` is `#rgb` or `#rrggbb`. Drives the workspace UI. |

`ActionSpec`:

| Field | Type | Required | Rule |
|-------|------|----------|------|
| `id` | string | yes | `^[a-z][a-z0-9_]*$`, unique within the manifest. |
| `phrases` | string[] | yes | At least one non-empty phrase. Natural-language triggers for the intent engine; mixed-language is expected (`"echo karo"`, `"repeat after me"`). |
| `input` | object | yes | Field name → type string (§4.2). May be `{}`. |
| `output` | object | yes | Field name → type string (§4.2). May be `{}`. |
| `irreversible` | boolean | yes | `true` → the brain must echo the plan and get explicit confirmation before running (publishing, sending mail, spending money). |
| `estimated_seconds` | integer | yes | `> 0`. Drives the user-facing countdown **and** the watchdog: default timeout is `2 × estimated_seconds`. |
| `cost_units` | integer | yes | `>= 0`. Charged by the brain on success; reported back in the result. |
| `needs` | string[] | yes | Names of other actions' `provides` this action requires. May be `[]`. Must not contain its own `provides`. |
| `provides` | string | no | Name of what this action produces in the planner graph. **Defaults to `id`**; the served manifest always includes the resolved value. |
| `optional` | boolean | no | `true` → the planner may skip this step. |
| `user_messages` | object | no | `{ started?, progress?, done?, failed? }`, all strings. Templates the brain renders with `{placeholders}` from input/output. The agent never renders these itself. |

Unknown keys are ignored by the reference validator but should not be relied on; add fields to this
document before shipping them.

### 4.2 Field types

The value in `input` / `output` is a **type string**, one of:

```
string   string[]   number   number[]   boolean   boolean[]   object   object[]
```

plus the same eight with a trailing `?` (`string?`, `object[]?`, …) meaning optional.

Runtime checking rules:

- `undefined` **and** `null` both count as absent. Absent + not optional → error; absent + optional → skipped.
- `object` means a non-null, non-array JSON object. Arrays are never `object`.
- `T[]` requires an array whose every element is a `T`.
- A field present in the value but absent from the schema is **allowed and ignored** — schemas are
  minimums, not exact shapes. Do not use `output` as an exhaustive contract for the UI.
- Numbers are JSON numbers; there is no integer type. Constrain in the handler if you need one.

Input is validated before the handler runs (failure → non-retryable error result). Output is validated
after it returns (failure → non-retryable error result, and the handler's value is discarded). Both
errors read `input.field is required (string)` / `output.field must be number`.

### 4.3 Compatibility

- Adding an action, or an **optional** input field, is a MINOR bump.
- Adding a required input field, renaming or removing anything, changing an output type, or changing
  `provides` is a MAJOR bump — the brain's stored plans reference these names.
- `estimated_seconds` and `cost_units` may change in a PATCH; they are estimates, not contract.

## 5. Callbacks

The agent POSTs to `callback_url` until the run is over. Two message kinds, one envelope each.

### 5.1 `kind: "event"`

Best effort, batched, **at most once** (no retry — a lost event message must never change the outcome
of a run). Events are buffered and flushed at most every `batchMs` (default **500 ms**), and the
buffer is flushed one last time before the result is sent. Batches are POSTed **sequentially**, so the
brain sees events in emission order, and always before the result.

`run_finished` and `run_error` are deliberately **excluded** from event batches — that information is
carried by the result message, so the brain has exactly one place to look for the outcome.

Always the **last** message of a run. Retried up to **3 attempts** with backoff (see §6).

`RunResult` fields:

| Field | Present when | Type | Meaning |
|-------|--------------|------|---------|
| `ok` | always | boolean | Discriminator. |
| `output` | `ok: true` | object | Validated against `actions[].output`. |
| `ms` | always | number | Wall-clock duration of the whole run, measured by the agent. |
| `cost_units` | `ok: true` | number | Copied from the action spec. Charge on success only. |
| `llm_calls` | `ok: true` | number | LLM calls made during the run. |
| `tokens_in` / `tokens_out` | `ok: true` | number | Token totals across those calls. |
| `error` | `ok: false` | string | Developer-readable. Never shown raw to the user — the brain renders `user_messages.failed`. |
| `retryable` | `ok: false` | boolean | §6. |

### 5.3 The callback receiver's obligations

- Respond `2xx` fast. The agent treats any non-2xx or a network error as a failure and (for results) retries.
- Be **idempotent**: a retried result can arrive twice. Key on `run_id` and ignore a result for a run
  already terminal.
- Tolerate an event batch arriving for a run whose result you have already stored (possible under a
  retry) — drop it, do not resurrect the run.
- Verify the signature before doing anything else (§3.2).

## 6. Errors, timeouts and retries

### 6.1 Inside the run

An action never throws out of `/run`; every failure becomes a result with `ok: false`.

| Cause | `retryable` |
|-------|-------------|
| Handler threw `AgentError(msg, retryable, code)` | as declared |
| Handler threw anything else | `false` |
| Timeout (`2 × estimated_seconds` by default) | `true` |
| Abort / cancellation requested by the brain | `false` (reported as `"cancelled"`) |
| Input failed schema validation | `false` |
| Handler returned output failing schema validation | `false` |
| Unknown action reaching the runner | `false` |

The handler receives an `AbortSignal` that fires on timeout or cancel; long loops must check it, and
any HTTP call it makes should be given the signal. A handler that ignores the signal still has its run
terminated — the runner races the handler against the abort — but its work leaks until it finishes.

`retryable: true` means "the same request may succeed if repeated" (timeouts, 5xx upstreams, rate
limits). `retryable: false` means "repeating this is pointless" (bad input, quota exhausted,
permission denied). The brain owns the retry policy and the attempt counter; the agent only classifies.

### 6.2 Delivering the result

| Message | Attempts | Backoff | On final failure |
|---------|----------|---------|------------------|
| `kind: "event"` | 1 | — | Dropped silently (best effort by design). |
| `kind: "result"` | 3 | 250 ms, then 500 ms | Reported to the agent's `onError` hook and logged; the run is lost from the brain's point of view. |

A non-2xx response counts as a failed attempt. Because delivery can still fail after three tries, the
**brain must run a watchdog**: any run with no result after `2 × estimated_seconds` plus a grace margin
is failed as `agent_timeout` and retried by the brain's own policy. Callback delivery is at-least-once
with a bounded number of tries, never exactly-once — idempotency on `run_id` is what makes it safe.

### 6.3 What the brain does with a 4xx from `/run`

`401` → misconfiguration, alert, do not retry with the same token.
`400` → bug in the brain's plan or a manifest mismatch; fail the task, do not retry.
`409` → already accepted; do nothing and wait for the callback.
`5xx` / network error → the run never started; retry the POST with the **same** `run_id` (dedupe makes
this safe).

## 7. Implementing this in another language

A conforming agent is roughly 150 lines of glue plus your handler:

1. **Serve the three routes.** Reject `/run` without a constant-time token match.
2. **Serve a normalised manifest** — resolve `provides` defaults before serving, and validate your own
   manifest at boot so a broken agent refuses to start rather than failing mid-plan.
3. **Answer 202 before doing any work.** Spawn a task/thread/goroutine; do not `await` it in the handler.
4. **Emit events with the common envelope** `{run_id, tenant_id, agent_id, at}` plus the type-specific
   fields; buffer them and POST batches at most every 500 ms, sequentially.
5. **POST exactly one result**, after a final event flush, retried 3× with 250/500 ms backoff.
6. **Sign every POST** with `HMAC-SHA256(secret, run_id + "." + status)` in lowercase hex.
7. **Validate input against the manifest before the handler and output after it**; both failures become
   `ok:false, retryable:false` results, not exceptions.
8. **Enforce your own timeout** at `2 × estimated_seconds` and report it as `retryable: true`.

The full event union, in one place:

| `type` | Extra fields |
|--------|--------------|
| `run_started` | `action: string` |
| `step_started` | `step_id: string`, `label: string` |
| `step_finished` | `step_id: string`, `ms: number` |
| `progress` | `step_id?: string`, `fraction: number` (0..1, clamped), `label?: string` |
| `data` | `step_id?: string`, `kind: string`, `payload: any` |
| `log` | `step_id?: string`, `level: "debug"\|"info"\|"warn"\|"error"`, `message_dev: string` |
| `run_finished` | `output`, `ms`, `cost_units`, `llm_calls`, `tokens_in`, `tokens_out` — local sinks only, **not** sent over the wire |
| `run_error` | `message`, `retryable`, `ms` — local sinks only, **not** sent over the wire |

Common envelope on every one of them: `run_id`, `tenant_id`, `agent_id`, `at` (ISO-8601 with
milliseconds and a `Z` suffix).

`data.kind` is a free string the UI keys a renderer off — `chunk`, `keyword`, `section`, `image`,
`score`, `lead`. Pick one per agent domain and keep the payload shape stable across versions; the UI
falls back to a JSON dump for unknown kinds.

## 8. Conformance checklist

`src/e2e.test.ts` in this package is the executable version of this checklist — it runs the echo agent
and a fake brain on two real sockets and asserts each line below.

- [ ] `GET /health` → 200, `ok:true`, `version` equals the manifest's.
- [ ] `GET /manifest` → 200 and passes manifest validation, with `provides` resolved.
- [ ] `POST /run` without a token → 401, **and no callback is ever sent**.
- [ ] `POST /run` with a bad body → 400 with a `details` array.
- [ ] `POST /run` with an unknown action → 400 listing the known actions.
- [ ] `POST /run` with a repeated `run_id` → 409.
- [ ] `POST /run` returns 202 in well under 100 ms for a run that takes hundreds of ms.
- [ ] Events arrive before the result, in emission order, each with the full envelope.
- [ ] The result arrives last, exactly once, with `ok`, `ms` and (on success) the validated output.
- [ ] `x-agent-id` is the manifest id; `x-run-signature` verifies for the correct status and fails for a
      tampered status, a different `run_id`, or a different secret.
